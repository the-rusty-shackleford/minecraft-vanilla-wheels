# D-0001 — A vehicle is data: one entity type, a flat profile, mirrored once at load

**Decision**: One `EntityType` (`vanillawheels:vehicle`) serves every vehicle; which one
it is, is the profile id in its synced data, resolved against the synced datapack
registry `vanillawheels:vehicle`. The profile is one flat JSON object; the record is
split into `Look` and `Kit` map codecs internally only because `RecordCodecBuilder`
stops at sixteen fields. Every bound lives in the record's compact constructor, so the
codec refuses a bad file naming the field. `handedness: left` mirrors the mesh and every
vector in the profile once, at load, and negates the rotation angles a reflection
flips; the renderer never sees a sign convention.

**Why**: The gun protocol proved that a datapack entry alone is enough when the protocol
ships a real implementation, and vehicle mods then need no Java, no registration and no
version coupling beyond a semver range. One entity type means a vehicle mod adds no
registry entries at all and a lowcodefml mod can ship one. The generator's bundle is
left-handed while Minecraft's entity frame is right-handed; mirroring at load, once,
keeps that fact out of the physics, the renderer and the tests.

**Alternatives rejected**: *An entity type per vehicle* -- a Java registration per
vehicle mod, which is what data-only rules out. *Nested JSON per subsystem* -- each
nesting level is a place for a pack author to mis-indent; the flat shape reads as a spec
sheet. *Mirroring in the renderer* -- every vector consumer would have to agree on it.
